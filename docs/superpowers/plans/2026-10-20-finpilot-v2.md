# FinPilot v2 Implementation Plan (Money Weather + credibility fixes)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox syntax.

**Goal:** Close the credibility gaps found in the self-assessment (unverified forecast claims, forecast skill, synthetic-only evidence, weak demo/deploy readiness) and add one memorable feature: **Money Weather**, a 60-day financial weather map with storm warnings, a pre-mortem "autopsy" of the failing futures, and "umbrella" interventions ranked by measured risk reduction, with a live lifestyle slider.

**Architecture:** A new deterministic engine `engines/weather.py` runs the existing weekday-matched Monte Carlo (common random numbers) and derives a daily risk calendar, storm runs, a cause attribution over the failing paths, and ranked interventions. A Meteorologist agent narrates it (grounded_or only). Weather claims are added to the Verifier's recomputable claim kinds so forecast advice is no longer evidence-only. Everything works with no LLM key.

**Tech Stack:** unchanged (Python 3.14 locally, FastAPI, LangGraph, pandas 3, numpy, vanilla JS UI).

## Global Constraints (carried from v1, still binding)

- All LLM calls go through `finpilot/llm.py` (Mesh API, `https://api.meshapi.ai/v1`, `MESH_API_KEY`). No other LLM client or endpoint.
- No number shown to users originates from an LLM: LLM prose passes `grounded_or`; recommendations pass the Verifier. Never present scripted/fake LLM output as a live run.
- LLM failure degrades, never crashes. The no-key path must stay fully working.
- Honest evaluation: never edit the generators or loosen quality floors to flatter numbers; report unflattering results; LLM-dependent numbers are never fabricated (no key exists in the build environment; those sections stay "not run").
- All dynamic UI text via `textContent`; no `innerHTML`/`insertAdjacentHTML`/`eval`/inline handlers (a test enforces this).
- Profile names validated with `^[A-Za-z0-9_-]{1,40}$`; inputs validated -> HTTP 400, never 500.
- Use `.venv/bin/python`; tests must stay green (`345 passed` at the start of this plan) and warning-free.
- Do not push, do not add remotes.

## Weather definitions (shared by tasks W1-W4)

- `buffer` (safety buffer, default): 7 days of average total spend = 7 * (mean daily discretionary spend over the model window + sum of |recurring outflows| per month / 30.4). User-overridable.
- `lifestyle` (spend scale, default 1.0, allowed 0.0..2.0): multiplies discretionary spend (separate from `cuts`).
- Day risk `p(d)` = fraction of simulated paths whose balance on day d is below `buffer`.
- Weather label: `clear` p<0.05, `cloudy` 0.05<=p<0.15, `rain` 0.15<=p<0.35, `storm` p>=0.35.
- Storm = maximal run of consecutive days with p >= 0.25.
- Failing path = a path that is below `buffer` on at least one day.

### Task W1: Weather engine

**Files:** Create `finpilot/engines/weather.py`, `tests/test_weather.py`. Modify `finpilot/engines/forecast.py` (add `spend_scale` and optional per-category detail to `monte_carlo`) and its tests.

**Interfaces (produce exactly these):**
- `forecast.monte_carlo(model, balance, horizon=60, n=1000, seed=0, extra_flows=(), cuts=None, spend_scale=1.0, detail=False)`; `spend_scale` must be finite and in 0..3 else ValueError; RNG consumption unchanged (CRN must hold across `cuts`/`spend_scale`/`extra_flows`); with `detail=True` the returned `Result` has `.disc_by_cat` (n x len(model.cats), total discretionary spend per path per category over the horizon, after cuts/scale) and `.disc_daily_total` unnecessary; default behaviour byte-identical for existing callers (existing tests unedited).
- `weather.default_buffer(model) -> float`
- `weather.risk_calendar(model, balance, horizon=60, n=1000, seed=0, buffer=None, lifestyle=1.0, cuts=None, extra_flows=()) -> list[dict]` one dict per day: `date` (ISO str), `p_below_buffer` (0..1, rounded 3), `label`, `p10`, `p50`, `p90` (rounded 2).
- `weather.storms(calendar) -> list[dict]` each `{start, end, days, peak_p, peak_date, label}` (peak_p rounded 3), sorted by peak_p desc.
- `weather.autopsy(model, balance, horizon=60, n=1000, seed=0, buffer=None, lifestyle=1.0, cuts=None, extra_flows=()) -> dict`: `{"p_any_breach": float, "n_failing": int, "n_paths": int, "causes": [...], "bills": [...], "first_breach": {"date": str|None, "share": float}}` where `causes` ranks discretionary categories by mean excess spend in failing paths vs non-failing paths: `[{"category","excess_per_path","failing_mean","other_mean","share_of_gap"}]` (top 5, shares sum to <=1, only positive excess), `bills` lists recurring outflows dated inside the horizon before the median first-breach day: `[{"merchant","date","amount"}]`, `first_breach` is the most common first-breach date among failing paths (None if no failing paths). If no path fails return empty `causes`/`bills`.
- `weather.umbrellas(model, balance, horizon=60, n=1000, seed=0, buffer=None, lifestyle=1.0, extra_flows=()) -> list[dict]`: candidate interventions = for each of the top 4 discretionary categories by mean daily spend, cuts of 10%, 20%, 30%; each `{"category","cut_pct","p_any_breach_before","p_any_breach_after","risk_reduction","monthly_sacrifice","reduction_per_1000"}` (monthly_sacrifice = mean daily category spend * 30 * cut, rounded 2; reduction_per_1000 = risk_reduction / (monthly_sacrifice/1000)); returns the best 3 by reduction_per_1000 among those with risk_reduction > 0 (empty if the baseline never breaches). Uses CRN so reductions are noise-free.
- `weather.report(model, balance, horizon=60, n=1000, seed=0, buffer=None, lifestyle=1.0, cuts=None, extra_flows=()) -> dict`: `{"buffer","lifestyle","horizon","calendar","storms","autopsy","umbrellas","headline": {"p_any_breach","worst_day","worst_p","n_storm_days"}}`. JSON-safe.

**Tests (write first):** constructed deterministic models (reuse the style in tests/test_forecast.py / test_simulate.py with persona data from `eval.generate`): labels at the thresholds; storms merges consecutive days and ignores isolated sub-threshold days; CRN: changing `lifestyle` from 1.0 to 0.8 never increases any day's `p_below_buffer`; `lifestyle` 0 gives fixed-flows-only paths; autopsy on a constructed model where one category obviously drives failure ranks it first and `share_of_gap` is positive; no failing paths -> empty causes/bills and `first_breach.date` None; umbrellas ordered by `reduction_per_1000` and each `p_any_breach_after <= p_any_breach_before`; `spend_scale` validation (nan, -1, 3.1 -> ValueError); report JSON-serialisable with `json.dumps`; determinism with the same seed; existing monte_carlo tests untouched and passing.

### Task W2: Verifiable weather and forecast claims

**Files:** Modify `finpilot/engines/verify.py`, `finpilot/agents/verifier.py`, `finpilot/agents/advisor.py`, `finpilot/graph.py`; tests in `tests/test_verify.py`, `tests/test_advisor_verifier.py`, `tests/test_graph.py` (+ new tests as needed).

**Purpose:** forecast/weather advice must stop being `evidence_only`. Add recomputable claim kinds and a context argument carrying the opening balance (the verifier previously saw only the dataframe).

**Interfaces:**
- `verify.recompute(claim, df, ctx=None)`, `verify.check_claim(claim, df, ctx=None)`, `verifier.audit(rec, df, ctx=None)`, `verifier.verify_all(recs, df, llm=None, emit=None, ctx=None)`; `ctx = {"opening": float}`. New claim kinds (all return percent values 0..100 or currency):
  - `breach_probability` `{horizon}` -> % of simulated paths below the default buffer at least once (re-fits the model from `df`, balance = `ctx["opening"] + df.amount.sum()`, seed 0, n 1000, same as the engine).
  - `storm_peak` `{date}` -> peak % `p_below_buffer` of the storm containing `date` (None if that date is not in a storm).
  - `storm_peak_after_cut` `{date, category, cut_pct}` -> the same storm peak after applying that cut.
  Without `ctx` (or when the model cannot be fit) these return None (unverifiable). Claims must be well-formed; malformed -> unverifiable (existing contract).
- Document in the module docstring that these claims re-run the same engine (consistency check, not an independent implementation), as already done for the spike aggregation.
- Advisor: `forecast_risk` candidate now carries a `breach_probability` claim and uses the weather headline numbers (peak day and storm window) in its evidence and template text; add a `storm_warning` candidate (trigger_type `storm_warning`) for the top storm (peak_p >= 0.25) with claims `storm_peak` and, when an umbrella exists, `storm_peak_after_cut`; template text e.g. "Storm warning: {start} to {end}, peak {peak}% chance of dropping below your safety buffer ({buffer}). Cutting {category} by {cut}% lowers the peak to {after}%." All numbers present in claims/evidence; templates must pass `audit`.
- `build_candidates(findings, df, forecast=None, goals=None, weather=None)`; the graph forecast node attaches `weather` (via `weather.report`) to state and `n_advise` passes it. The forecast dict still has no `model`. `state["weather"]` is JSON-safe and persisted with the forecast blob (`service._persist`).

**Tests (write first):** each new kind recomputes correctly vs the engine on persona data; malformed/ctx-missing -> unverifiable; a rec whose text lies about the storm peak is caught and corrected; `forecast_risk`/`storm_warning` recs are `verification == "recomputed"`; every template passes audit; the graph pipeline test shows storm_warning rec verified on a persona/scenario that has a storm (construct one by lowering opening balance via the request if needed; the pipeline accepts `opening`).
